# DSH 版本升级对照评估（2026-10-17）

## 这个文档解决什么问题

分镜规划链路当前把 DSH 固定在 Python SDK `0.1.5rc1`。社区路线已推进到 `0.2.x`，直觉上"新版本分镜质量更好、还能顺手干掉一堆工具风险"。

本文档是**一次真实对照实验的存档**，回答三个问题：

1. `sdk` profile 到底给模型开了哪些工具，安全边界在哪；
2. 换到 `0.2.x` 后，跑通同一个分镜任务会遇到什么；
3. 现在该不该升。

结论先行：**NO-GO，保持 0.1.5rc1。** 不是因为质量差，是因为 `0.2.x` 在 DeepSeek 公共 API 上连一次有效输出都产生不了。

---

## 一、实验设置

公平对照的前提是两组必须共用同一套 prompt 构建 / 解析 / 校验 / 重试逻辑，否则比出来的差异分不清是版本差异还是实现差异。

| | A 组（现状） | B 组（候选） |
| --- | --- | --- |
| DSH 版本 | Python SDK `0.1.5rc1` | npm `@deepseek-ai/dsh` `0.2.1-rc.2` |
| 入口 | `scripts/dsh-storyboard/main.py` | `dsh --profile headless` CLI |
| 注入方式 | `DeepSeekHarnessConfig(api_key=..., base_url=...)` | env `DEEPSEEK_API_KEY` / `DEEPSEEK_BASE_URL` |
| profile | `sdk` + `profile/cordis.patch.yml` | `sdk` + patch 自动转换版 |
| 共用逻辑 | `planStoryboard(input, run)` 的 `RawRunner` 注入点 | 同左 |

共用逻辑的关键签名（A/B 两组的公平性来源）：

```ts
export function buildStoryboardPrompt(input: StoryboardPlanInput): string
export async function planStoryboard(
  input: StoryboardPlanInput,
  run: RawRunner,
): Promise<StoryboardPlanResult>
```

`RawRunner` 让两组注入各自的执行方式，而 prompt、重试（`attempt <= 2`，失败时追加 `buildRetryPrompt`）、`verifyChartSpecs` 校验全部是同一份代码。

**实验输入**（两组完全一致）：

- 文章 URL：`https://mobile.zol.com.cn/1260/12606026.html`
- 提示词：`阅读这篇文章 对该产品制作一个介绍短视频，要结合文章内容制作丰富的图表 并配合解说`
- 时长：`durationSeconds` 取默认值
- 5 张图素材；`outroText` 未传（`pipeline.ts` 的 `buildBeats` 路由里本就未传）

## 二、实验结果

| 组别 | 结果 | 耗时 |
| --- | --- | --- |
| A 组 `0.1.5rc1` | 成功，返回 `收到。` | 9.7s |
| B 组 `0.2.1-rc.2` | 失败：`HTTP 404: DeepSeek Messages request failed` | 1.6s |

B 组 1.6s 就返回 404，说明请求**根本没进模型**，是协议层被拒，不是模型能力不足。

### 三层排障

**第一层：凭据是否有效？**

绕开 DSH，直接打 DeepSeek 公共 API：

| 请求 | 结果 |
| --- | --- |
| `POST /v1/chat/completions` | **HTTP 200** |
| `POST /v1/messages` | **HTTP 404** |

key 有效，网络通。问题在端点。

**第二层：换 baseUrl 能否绕过？**

逐个试三个候选，全部 404：

- `https://api.deepseek.com`
- `https://api.deepseek.com/v1`
- `https://api.deepseek.com/v1/`

**第三层：根因**

`0.2.x` 起官方适配器只走 **Messages API**（v0.1.7-rc.1 起明确"旧 protocol 配置和 Chat Completions 地址需迁移"），而 **DeepSeek 公共 API 只暴露 OpenAI 兼容的 `/v1/chat/completions`，不存在 `/v1/messages` 端点**。

这不是配置错误，是协议层断裂。换 URL 换不来，因为缺的是端点而不是路径前缀。

## 三、被这次实验打掉的三个未知数

虽然是 NO-GO，但排障过程本身消灭了三个原本悬而未决的问题——将来若 DeepSeek 补上 Messages 端点，或改走自建中转，这三条可以直接用。

### 1. CLI headless 契约与 `main.py` 几乎完全一致

`dsh --profile headless [task]`：`-` 从 stdin 读任务，答案走 stdout，诊断走 stderr，`--json` 输出 NDJSON 事件流；`--patch` 是可重复的一等参数。

与现有桥接的协议（stdin 收 JSON / stdout 出 JSON / 退出码永远 0）**形状一致**，`src/lib/dsh.ts` 的 spawn 层不需要重写。

> 反直觉点：`run()` 没有 timeout 参数，超时在 `request_timeout_seconds`；`dsh_home` 是必填项；profile 默认是 `sdk` 而非 `sdk-minimal`，自带全套工具必须靠 patch 逐个禁用。

### 2. headless 默认模型就是 `deepseek-flash`

与用户侧模型配置一致，不需要额外覆盖。

### 3. patch 只需改 2 行就能在 0.2.x 生效

| 改动 | 原因 |
| --- | --- |
| `- id: workflow-worker-thread` → `- id: workflow-ptc` | v0.1.7-rc.1 上游改名 |
| 删除 `- id: tool-ralph` | v0.1.7-rc.1 起"默认不再启用 Ralph"，条目已移除 |

**行为差异值得注意**：0.2.x 对未知 patch 条目是**硬失败并指名道姓**（`N entries did not activate`），不再是 0.1.5rc1 的静默失效。这意味着升级时失效的 id 不会再悄悄放过——好事，但也意味着一条过期 id 就起不来 profile。

## 四、`sdk` profile 的工具安全边界

这部分是升级评估的前置项，独立于 A/B 结果有效。

### 危险不是沙箱，是工具入口

DSH 的 "Everything is a Plugin" 架构里，**沙箱和权限 service 不可禁用**。实测依赖链：

```
subprocess → bash-sandbox / pwsh-sandbox → shell → permission-presets
commands  → command-compact
approval  → permission-presets
```

关掉其中任何一个，profile 启动即报 `waiting for service: subprocess|shell`。所以"把沙箱关掉以获得安全"的方向从一开始就不成立。

真正决定暴露面的是**工具入口插件**，命名约定为 `tool-` 前缀：禁用入口后，对应 service 变为 inert。

### 审计结论（源码级全量扫描）

扫描判据是硬特征，不靠命名猜：

```ts
ctx.tools.register(defineTool({ name: "..." }))          // 同步注册
yield ctx.tools.register(defineTool({ ... }))            // 生成器注册
```

| 指标 | 数量 |
| --- | --- |
| 扫描包总数 | 294 |
| 实际注册工具的包 | 26 |
| 出现在 `sdk` profile 中的 | 12 |
| 已禁用 | 11 |

已禁用清单：`tool-bash` `tool-fs` `tool-fs-search` `tool-goal` `tool-jobs` `tool-pwsh` `tool-skill` `tool-subagent` `tool-subagent-control` `tool-todo` `tool-web`。

另有 13 个此前以为暴露、实际**根本不在 `sdk` profile 里**的工具插件：`tool-agent-team` `tool-terminal` `tool-worktree` `tool-session-query` `tool-schedule` `tool-cordis` `tool-bash-persistent` `tool-pwsh-persistent` `tool-present` `tool-ask-user` `tool-str-replace-editor` `tool-workspace-dependencies`。

还有 6 个此前被列为"危险且未禁用"的插件（`skill-office` `remote-access` `workflow-ptc` `ptc-runtime` `config-editor` `web-deepseek-api`），实测**一个工具都没注册**，是纯 service 或配置层。

### 真实漏网 2 个

| 插件 | 注册的工具 | 当前严重性 | 形状风险 |
| --- | --- | --- | --- |
| `tool-working-directory` | `working_directory` | 低 | 能读 cwd、`cd`；读不到文件内容（`tool-fs` 已禁） |
| `mcp-resources` | `list_mcp_resources` / `list_mcp_resource_templates` / `read_mcp_resource` | 低（完全空转） | **不以 `tool-` 开头**，一旦配 MCP server 就自动激活 |

`mcp-resources` 当前空转的三个条件：profile 无 `config:` 块、项目无 MCP server 配置、代码有 `isEmpty()` 守卫。

**为什么这个漏网值得记一笔**：黑名单模型的失效模式在这里暴露得很彻底——靠命名和前缀推断风险是不可靠的，`mcp-resources` 不符合任何命名约定，却注册了 3 个工具。判定必须落到源码特征上。

> 方法论修正记录：首轮严格正则漏掉了 `mcp-resources`，因为它用生成器写法注册，且 cordis id 提取正则对它返回 `null`，求交时被过滤。当时得出"只有 1 个漏网"，逐个读源码验证后更正为 **2 个**。

## 五、实验中的两个额外发现

### `web-deepseek-api` 激活告警（依赖漂移）

patch 禁掉 `web` service 后，`web-deepseek-api` 会挂起等待它。这是 0.1.5rc1 时代建立的依赖图在 0.2.x 漂移的直接证据——**「哪些能禁哪些不能禁」的经验规则不是跨版本稳定的**，升级时必须重新实测，不能照抄。

### Windows spawn EINVAL

```ts
// 错：Windows 上 shell:false 执行 .cmd 报 EINVAL
spawn("...\\dsh.cmd", { shell: false })
// 对：直接跑 JS 入口
spawn(process.execPath, [DSH_CLI, ...args])
```

`DSH_CLI` 指向 `@deepseek-ai/dsh/lib/bin.js`（来自 `package.json` 的 `"bin": {"dsh": "lib/bin.js"}`）。这是将来真要切 0.2.x 时第一个会踩的坑。

## 八、结论与建议

1. **保持 `0.1.5rc1`，不升 0.2.x。** 阻塞原因是协议断裂，不是质量问题——"0.2.x 分镜质量更好还是更差"这个问题在当前配置下**无法回答**，因为 B 组一次有效输出都产生不了。
2. **`profile/cordis.patch.yml` 保持原样。** 实验全程未改动（`git diff --stat` 为空），实验用的是临时转换副本。
3. **顺手修掉 4 处 patch 问题**（与升级决策解耦，现在就能做，纯安全收益）：

   | 修复 | 性质 |
   | --- | --- |
   | `tool-working-directory` 加入禁用 | 补漏网 |
   | `mcp-resources` 加入禁用 | 补漏网（且形状危险，不合命名约定） |
   | `workflow-worker-thread` → `workflow-ptc` | 失效 id，为 0.2.x 预留 |
   | 删除 `tool-ralph` | 失效 id，为 0.2.x 预留 |

   后两条只影响 0.2.x 行为，对 0.1.5rc1 无害（0.1.5rc1 对未知条目静默失效），可提前做掉。

4. **`dsh-upgrade-preflight` 预检脚本值得做。** 本次实验的最大成本不是跑实验，是**靠人肉试错才定位到协议层**。一个预检脚本（依次验证端点存在性 / 凭据有效性 / patch 条目激活情况 / 工具暴露面 diff）能把这次的排查时间从小时级压到分钟级，且下次升级能直接复用。
